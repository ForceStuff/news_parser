# news_parser

Самостоятельный микросервис сбора новостей. Первый адаптер: **ФСП России**, источник
<https://fsp-russia.ru/press/news/>. Календарь мероприятий не парсится.
Все файлы проекта находятся в `news_parser`; код и конфигурация соседних сервисов не изменяются.

## Что реализовано

- FastAPI, OpenAPI/Swagger `/docs`, API-ключ `X-API-Key` на всех `/api/*`.
- Собственная БД: источники, статьи, изображения, задания, состояние экспорта.
- PostgreSQL для развёртывания, SQLite для локального запуска; миграции Alembic.
- Отдельный worker, долговечная очередь в БД, восстановление после перезапуска.
- Разбор списка и отдельных статей ФСП: заголовок, текст, дата, источник, картинки.
- Пагинация и фильтры API, редактирование текста, защита ручных правок от перепарсинга.
- Дедупликация по источнику и каноническому URL; хеш для обнаружения изменений.
- Загрузка картинок в существующий `file_service`, преобразование JPEG/PNG/WebP в WebP.
- JSON для ручной интеграции с `news_service` и отдельный управляемый экспорт черновиков.

Статьи возвращаются с `body_format=plain_text`: текст без исполняемой HTML-разметки.
Изображения возвращаются отдельным массивом, первое — обложка. Исходная дата
`source_published_at` хранится отдельно от даты публикации в вашем CMS. Даты API — UTC.

## Быстрый запуск в Windows / PowerShell

Все команды выполняются **из `news_parser`**. Нужен Python 3.12+.

```powershell
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

В `.env` замените `API_KEY` на длинный случайный ключ. Затем:

```powershell
.venv/Scripts/alembic upgrade head
.venv/Scripts/uvicorn app.main:app --host 127.0.0.1 --port 8002
```

В другом терминале, из той же папки:

```powershell
.venv/Scripts/python -m app.worker
```

Swagger: <http://localhost:8002/docs>. Нажмите **Authorize** и укажите `API_KEY`.
Миграция уже добавляет источник ФСП с ID `c9d743f6-c603-4d37-a911-51f98e718c60`.
API сам не создаёт таблицы: перед запуском применяются миграции.

Пример полного сценария через API:

```powershell
$headers = @{ 'X-API-Key' = 'ваш-ключ-из-env' }
$base = 'http://localhost:8002'
$sources = Invoke-RestMethod "$base/api/sources" -Headers $headers
$body = @{ source_id = $sources[0].id; limit = 3; max_pages = 1 } | ConvertTo-Json
$job = Invoke-RestMethod "$base/api/parse-jobs" -Method Post -Headers $headers `
    -ContentType 'application/json' -Body $body
Invoke-RestMethod "$base/api/jobs/$($job.id)" -Headers $headers
# После обработки задания worker:
$articles = Invoke-RestMethod "$base/api/articles?page=1&size=20" -Headers $headers
$id = $articles.items[0].id
Invoke-RestMethod "$base/api/articles/$id" -Headers $headers
Invoke-RestMethod "$base/api/articles/$id/export" -Headers $headers
```

Для конкретной статьи передайте `urls` в `POST /api/parse-jobs`:

```json
{
  "source_id": "c9d743f6-c603-4d37-a911-51f98e718c60",
  "urls": ["https://fsp-russia.ru/press/news/SLUG/"],
  "limit": 20,
  "max_pages": 1
}
```

Если `urls` непустой, обрабатываются перечисленные URL (до 500); `limit` и `max_pages`
ограничивают только поиск по списку. Запуск по расписанию можно организовать внешним
планировщиком, вызывающим этот же эндпоинт. Встроенного расписания в первой версии нет.

## Просмотр результатов локального теста

При работающем API можно сформировать HTML-снимок завершённого задания (его UUID
возвращает `POST /api/parse-jobs`):

```powershell
.venv/Scripts/python -m scripts.demo_report --job-id UUID-ЗАДАНИЯ
.venv/Scripts/python -m http.server 8003 --bind 127.0.0.1 --directory .scratch/preview
```

Откройте <http://127.0.0.1:8003/>. Отчёт содержит поиск, полные тексты, ссылки на оригиналы
и `results.json`. В нём нет API-ключа. Картинки, ещё не сохранённые в `file_service`,
показываются напрямую с сайта-источника с отдельным пояснением. Это статический снимок:
после нового парсинга нужно повторить команду формирования отчёта.
Swagger доступен на <http://127.0.0.1:8002/docs>; для `/api/*` в Authorize укажите
значение `API_KEY` из локального `.env`.

## Docker / PostgreSQL

Создайте `.env` и задайте `API_KEY` и `POSTGRES_PASSWORD` (для URI используйте
буквы и цифры либо корректно URL-кодируйте пароль). Затем:

```powershell
docker compose up --build -d
docker compose logs -f worker
```

Compose поднимает только БД парсера, миграции, API и worker. Данные PostgreSQL — в отдельном
томе `parser-db`; порт БД наружу не опубликован. API привязан к `127.0.0.1:8002`.
В Docker `DATABASE_URL` задаётся compose и переопределяет SQLite из `.env`.

Адреса соседних сервисов задавайте доступными **из контейнера**. Для сервисов на хосте:
`FILE_SERVICE_URL=http://host.docker.internal:8001`,
`NEWS_SERVICE_URL=http://host.docker.internal:8000` — порты замените своими.
`FILE_PUBLIC_URL` должен быть доступен потребителю API, например браузеру.
Существующие сервисы этот compose не запускает и не перенастраивает.

## Совместный локальный тест с настоящим file_service

Из `news_parser` при работающем Docker Desktop:

```powershell
.venv/Scripts/python -m scripts.configure_files
docker compose --env-file .scratch/runtime/integration.env -f compose.integration.yml up --build -d
```

Затем перезапустите API и worker парсера, чтобы они прочитали новый токен из `.env`.
Тестовый `file_service` доступен на `http://localhost:8001`, его PostgreSQL и файлы
хранятся в отдельных постоянных Docker-томах. Сборка читает оригинальный `../file_service`;
его исходники и настройки не редактируются. Внешний реестр `integration/file-services.json`
монтируется только для чтения и регистрирует идентичность `news-parser` с отдельным токеном.
Пароли находятся в игнорируемом `.scratch/runtime/integration.env`.

Запустите новое задание парсинга через API. После его завершения:

```powershell
.venv/Scripts/python -m scripts.verify_files --job-id UUID-ЗАДАНИЯ
.venv/Scripts/python -m scripts.demo_report --job-id UUID-ЗАДАНИЯ
```

Проверка читает метаданные и бинарные файлы из настоящего `file_service`, проверяет
формат WebP, размеры, длину содержимого и запрет доступа к внутреннему API без токена.
Отчёт `.scratch/runtime/files-verification.json` содержит ID и контрольные суммы файлов.
Остановка тестовых контейнеров с сохранением данных:

```powershell
docker compose --env-file .scratch/runtime/integration.env -f compose.integration.yml down
```

## Эндпоинты

Все `/api/*` требуют `X-API-Key`; ошибки валидации — 422, отсутствующий объект — 404.
Создание задания возвращает **202 + ID**, обработка выполняется worker.

| Метод и путь | Назначение |
|---|---|
| `GET /health`, `GET /ready` | Процесс жив / БД, миграции и ключ настроены |
| `GET /api/adapters` | Поддерживаемые адаптеры |
| `GET /api/sources` | Источники |
| `POST /api/sources` | Добавить источник: `name`, `adapter`, `url` |
| `PATCH /api/sources/{id}` | Изменить название или `enabled` |
| `POST /api/parse-jobs` | Поставить парсинг в очередь |
| `GET /api/parse-jobs/{id}` | Состояние задания (алиас `/api/jobs/{id}`) |
| `GET /api/jobs` | История с `page`, `size` |
| `POST /api/jobs/{id}/retry` | Новое задание на повтор неудачного/частичного запуска |
| `GET /api/articles` | Список: `source_id`, `q`, `published_from`, `published_to`, `page`, `size` |
| `GET /api/articles/{id}` | Статья, изображения и результат экспорта |
| `PATCH /api/articles/{id}` | Исправить `title` / `body`; защитить их от перепарсинга |
| `POST /api/articles/{id}/images/retry` | Повторить загрузку неудавшихся изображений |
| `GET /api/articles/{id}/export` | `news_create`, источник и метаданные изображений |
| `POST /api/articles/{id}/export` | Экспортировать черновик; тело `{"tags": []}` |
| `POST /api/articles/{id}/export/reconcile` | Разрешить неопределённость создания новости |
| `POST /api/images/{id}/reconcile` | Разрешить неопределённость загрузки изображения |

Статусы задания: `queued → running → completed / partial / failed`.
`result.article_ids` содержит сохранённые статьи, `result.errors` — ошибки отдельных URL/картинок.
Если `file_service` недоступен или токен не задан, текст сохраняется, задание становится
`partial`, у картинок будет `failed`. После настройки сервиса вызовите `images/retry`.
Ошибка загрузки одной статьи не отменяет остальные.

## Контракт file_service — без изменений его кода

Используются только:

- `POST /internal/upload` — multipart `file`, `is_public=true`, заголовок `X-Internal-Token`;
  ожидается 201 с `file_id` (UUID).
- `GET /files/{file_id}` — чтение публичного изображения, включая HTTPS-переход на объектное хранилище.

Постоянные бинарные данные находятся только в `file_service`, в БД парсера — ID и метаданные.
Загрузка и нормализация выполняются в памяти с лимитами. По умолчанию исходник до 20 МиБ,
результат до 5 МиБ, размер изображения до 1920×1080. Анимация и SVG не принимаются.

**Требование развёртывания:** `FILE_SERVICE_TOKEN` должен быть явно выдан парсеру владельцем
инфраструктуры и распознаваться существующим реестром `file_service`. В предоставленном
реестре `news_parser` отсутствует. Этот проект не изменяет реестр и не копирует токен
`news-service`. Пока доступ не выдан, загрузка невозможна; это отражается в API.
Завести отдельную сервисную идентичность можно настройкой развёртывания файлового сервиса,
но такие изменения не входят в данный проект.

## Контракт news_service — без изменений его кода

`GET .../export` всегда доступен и ничего не отправляет. Его `news_create` содержит ровно:
`title`, `body`, `status="draft"`, `tags`, `published_at=null`.
`tags` — UUID уже существующих тегов **news_service**, а не строки с сайта.

Отправка выключена по умолчанию: `NEWS_EXPORT_ENABLED=false`.
В текущем `APP_MODE=PUBLIC_MVP` сервис новостей блокирует запись через HTTP (404).
Включение экспорта в парсере не обходит это ограничение.

Когда доступный экземпляр `news_service` разрешает запись:

1. Настройте URL и `NEWS_EXPORT_ENABLED=true`.
2. Для существующего gateway задайте `NEWS_BEARER_TOKEN` администратора.
   Для доверенной внутренней сети допустимы `NEWS_USER_ID` (UUID) и `NEWS_USER_ROLES=admin`;
   такие заголовки нельзя принимать за авторизацию на публичном периметре.
3. `POST /api/articles/{id}/export` создаст задание. Worker вызывает
   `POST /api/news`, сохраняет полученный ID и отдельно вызывает `PUT /api/news/{id}/cover`.

Передать готовый `cover_image_id` текущий контракт не позволяет. Поэтому обложка
скачивается из `file_service` и передаётся бинарным файлом; `news_service` сохраняет
свою копию. Все остальные изображения остаются доступны через API парсера: галереи
в контракте `news_service` нет. Автоматической публикации и обновления уже
экспортированной новости нет, редакторские изменения CMS не перезаписываются.

Если черновик создан, но обложка не установлена, сохраняется `cover_pending` и `news_id`.
Повтор продолжает установку обложки, не создавая ещё одну новость.

## Восстановление и ограничения

В первой версии работает **один worker**. В PostgreSQL это обеспечивается advisory lock,
в SQLite — блокировкой файла ОС. API может обслуживать несколько запросов одновременно.
`python -m app.worker --once` обработает максимум одно задание и завершится.
После перезапуска прерванный парсинг переходит в очередь; уже записанные статьи и картинки
переиспользуются. Для нескольких параллельных обработчиков нужно будет расширить
протокол захвата заданий и ограничение частоты запросов к сайтам.

Существующие API загрузки файлов и создания новостей не предоставляют пригодной парсеру
общей гарантии идемпотентности. Если POST мог завершиться, но ответ потерян, результат
помечается `unknown`; автоматический повтор запрещён. Проверьте внешний сервис и вызовите
соответствующий `reconcile` с одним из тел:

```json
{"remote_id": "UUID-найденного-файла-или-новости"}
```

```json
{"confirmed_absent": true}
```

Второй вариант — явное подтверждение оператора, что объект **не создан**; иначе повтор
может создать дубликат. Во время активного задания сверка запрещена. После сверки
повторите экспорт или загрузку изображений. Файлы автоматически не удаляются: удаление
может сломать ссылки других потребителей. Неактуальные изображения остаются в метаданных
с `active=false`; политика хранения/очистки — отдельное расширение.

Защита загрузчика: HTTPS и список доменов адаптера, запрет private/loopback/link-local IP,
проверка каждого редиректа, закрепление проверенного IP при соединении (защита от DNS
rebinding), ограничения объёма и времени, ограничение частоты, ограниченные повторы GET.
Переменные прокси из окружения не используются. При сетевом разрыве с PostgreSQL
во время внешнего запроса распределённая гарантия exactly-once отсутствует.

Особенности ФСП: на проверенной странице есть 16 карточек, а «Больше событий» имеет пустой
`href`. Адаптер следует только реальным ссылкам пагинации; полную историческую выгрузку
сайт этим списком не гарантирует. Обложка берётся из карточки списка. Для переданного
вручную старого URL, отсутствующего в списке, доступны только изображения самой статьи.
При изменении HTML-селекторов задание сообщает об ошибке вместо сохранения страницы меню.

## Добавление другого сайта

1. Создайте адаптер в `app/adapters/`, реализующий `Adapter` из `base.py`.
2. Определите доверенные домены, проверку URL, `discover()` и `parse()`.
3. Верните `ParsedArticle`: канонический URL, заголовок, обычный текст, дату с часовым поясом,
   URL изображений (обложка первой).
4. Зарегистрируйте класс в `ADAPTERS` и добавьте источник через `POST /api/sources`.
5. Добавьте синтетические HTML-фикстуры и тесты. API, worker и клиенты других сервисов
   при этом менять не требуется.


Тесты используют отдельную SQLite и HTTP-заглушки; они не меняют соседние сервисы.
Интеграция с реально развёрнутыми сервисами требует их URL, разрешённого токена файлового
сервиса и доступного API записи новостей. Docker/PostgreSQL необходимо проверять на хосте
с работающим Docker Engine.
